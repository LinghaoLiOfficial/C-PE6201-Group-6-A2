# D2(a) 工具打分表 —— 8 个工具，逐个过「3 个问题」

> 作业要求：每个工具用 Class 4 的三个问题打分，做成表格放进 repo。
> 三个问题：① 缺了它任务会失败吗？② 模型会把它和邻居搞混吗？③ 它从没被调用时成本是多少？

## 先回答第三问（对 8 个工具是同一个答案）

每个工具的「说明书」都写在提示词的固定前缀（`TOOL_SPEC`）里，**每轮都重发、重计费，调不调用都一样**。我们的设计是：每个工具**只写一行签名**（约 25~35 token），8 个工具加起来约 300 token 的前缀。

→ 结论：前缀成本是「恒定小成本」，因为每个工具的描述都短到只剩签名。**工具越多、描述越啰嗦，这个隐性成本越大**——这正是我们坚持「一行签名」的原因。

## 8 个工具打分表

| 工具 | ① 缺了会失败吗？ | ② 会和邻居搞混吗？ | 为什么配得上这个位置 |
|------|-----------------|-------------------|---------------------|
| **get_claim** | **会** —— 没它连 member_id / hospital_id / code 都拿不到，后面全断 | **不会** —— 唯一入口 | 入口。所有查询都靠它给出的 id 往下走 |
| **lookup_member** | **会** —— 唯一的 member_id→policy_id 之桥 | **不会** —— 故意**只返回 policy_id**（不返回 name/join_date），就是为了不给模型多余信息 | 唯一的桥。但注意：作业说「这一跳没有任何决策信息」，是我们**最该反思能不能省**的工具（见下方反思） |
| **lookup_policy** | **会** —— status/日期/headroom/exclusions 的唯一来源 | **不会** | 作业原话「**大部分拒赔都来自这一行**」，三个拒赔理由全在这 |
| **get_hospital_status** | **会** —— panel 的唯一来源 | **不会** | panel=false 会改变结果，必须查，不能静默通过 |
| **check_procedure** | **会** —— requires_preauth 的唯一来源 | ⚠️ **会，和 get_preauthorisation 易混** | 它是「**要不要**预授权」的分支开关，决定 run 长不长 |
| **get_preauthorisation** | **会** —— 预授权的唯一来源 | ⚠️ **会，和 check_procedure 易混** | 它是「**有没有**预授权 + 有效期」——只有 check_procedure 说 true 才查 |
| **check_documents** | **会** —— 所需材料的唯一来源 | **不会** | 把「缺材料」变成 **ask**，而不是误判成 refuse |
| **check_duplicate** | **会** —— 查重的唯一来源 | **不会**（但和 get_claim 都吃 claim_id，签名上已区分） | 唯一能认出「重交」的工具；必须比对四项事实，不能只看 claim_id |

## 两个诚实的反思（写进报告加分）

**1. 我们没有 search_notes 式「陷阱工具」。**
作业用 Class 4 的 `search_notes` 举例：一个「缺了也不会失败、又容易和邻居搞混」的工具，最后正是它导致 agent 出错。我们 8 个工具**每一个都是对应事实的唯一来源**，没有冗余——这本身就是「最短必要清单」的证明。代价是：没有现成的「可砍工具」来展示「砍掉一个工具」这个动作。

**2. lookup_member 是纯桥，是最该论证「能不能合并」的工具。**
作业给的四个省工具招数里，第二条是「**一个调用多返回点东西，别加第二个查找**」。`lookup_member` 只返回 policy_id，不返回任何决策信息（作业原话：「the first one carries no decision information at all」）。所以一个可论证的改造是：**让 `get_claim` 顺带返回 policy_id，砍掉 lookup_member**，8 个工具变 7 个，还少一跳。我们没有这么做，是因为保持「一个工具一个柜子、职责单一」更利于模型判别——但这**正是一个可以写进报告的「我们试过/考虑过合并，最终选择保留」的设计判断**，作业明确说「说你试过哪几招」。
